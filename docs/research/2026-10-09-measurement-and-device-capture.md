# Measurement and iPhone capture research — 2026-10-09

**Recommendation:** first make the browser capture and shelf inventory dependable, then prove metric spine measurements on one calibrated shelf plane. Treat whole-room reconstruction as an independent unresolved experiment. A native RoomPlan extension is a credible later consumer-product direction, but it is outside the approved browser-only assignment. User-supplied dimensions can improve a future consumer workflow; they cannot substitute for the assignment's same-sweep measurement evidence.

This note uses primary specifications and vendor documentation checked on 2026-10-09. Recommendations are engineering inferences, not measured accuracy results. No dependencies, hosted model calls, camera sessions or product-code changes were made for this research.

## What exists and what remains unproved

- `preflight/measure.py` implements `measure_spine_cm(marker_quad, spine_quad, *, same_plane)` with a portrait A4 destination of 21 × 29.7 cm. It returns height/thickness or `None`. It validates finite convex quadrilaterals, but **trusts the caller's plane assertion**; it does not detect the marker, detect spine corners, establish coplanarity, model lens distortion, or provide error bounds.
- `preflight/probe_measure.py` compares manually annotated corners with tape truth and leaves room measurements null. This is an evaluation probe, not an automatic product measurement pipeline.
- `backend/web/lifecycle.js` requests an environment camera at ideal 640 × 480. `backend/web/capture.js` draws at `video.videoWidth`/`video.videoHeight`, encodes JPEG at quality 0.85, and samples at 1 s intervals with one upload in flight. Higher upload latency causes skipped sampling opportunities.
- Existing owner-run evidence is summarized in [preflight results](../preflight-results.md): the 59-book trial saved 117 portrait 480 × 640 frames; metric A4/tape results remain **BLOCKED / NOT MEASURED**. Browser duration/delivery evidence at the lower resolution does not establish higher-resolution continuity.

Local verification on 2026-10-09: `.venv/bin/python -m pytest tests/preflight/test_measure.py -v` → **7 passed**, 0.17 s; `.venv/bin/python -m preflight.probe_measure --help` exited successfully. Python reports OpenCV **4.14.0**, `cv2.aruco` and `ArucoDetector` available. No installation is needed to explore those APIs locally, although their behavior in this project is untested. Official OpenCV tutorial URLs resolved to version 4.13.0; API examples must be checked against the installed version.

## Camera resolution is evidence, not a requested setting

The W3C capture specification distinguishes requested constraints from actual track settings. `getSettings()` supplies current settings; ideal dimensions are preferences, and rotation can affect reported dimensions. It is a capture configuration interface, not a calibrated camera intrinsic matrix or LiDAR depth feed. Do not derive focal length, metric distance or room size from a camera label, screen size or image resolution. [Media Capture and Streams](https://www.w3.org/TR/mediacapture-streams/)

**Proposed experiment:** compare the existing mode with ideal 1280 × 720 and 1920 × 1080 modes on the same real iPhone/Safari and secure origin, in separate complete camera+voice+upload runs. These resolutions are candidates, not guaranteed modes or performance promises. Log requested constraints, `getSettings()` after startup and orientation changes, actual canvas dimensions, encoded bytes, capture time, upload latency, preview freshness, sampling skips, voice interruptions and received frames. Feature-detect optional APIs; surface a degraded capture mode when constraints cannot be met. Preserve original evidence frames and crop from them, rather than reading text from a small voice-context image.

Changing resolution alone cannot recover missed shelf coverage. Separate preview/voice sampling from durable inventory evidence and record capture → saved → selected → analyzed frame counts. A bounded evidence queue/keyframe strategy must preserve novel shelf coverage while avoiding an unbounded post-sweep backlog. This is a proposed integration requirement; the current sampler does not implement it.

## Which metric approaches are credible?

| Approach | Can support | Required evidence and limits | Proposed disposition |
|---|---|---|---|
| Plain A4 quadrilateral + planar homography | Height/thickness in the observed spine plane | Known upright paper orientation, visible corners, marker physically in the spine plane, trustworthy spine corners; distortion/parallax tested | Keep the approved baseline and prove it before automating |
| ArUco reference of verified physical size | Repeatable marker identity and detected corners for local planar scale | Printed size checked physically; marker plane still has to match target plane | Alternative probe if plain-paper detection proves unreliable; not a committed replacement |
| ChArUco board | More calibration correspondences and refined corners, including some partial-board views | A printed board and capture/calibration procedure; extra consumer friction | Prefer as a development calibration aid before choosing it for runtime |
| Known user-supplied shelf/room dimension | Consumer-assisted scale or room records | Explicit units, who supplied it, when, what object/segment it describes | Later optional mode; separate from automatic assignment results |
| Native RoomPlan/ARKit | Sensor-backed room surfaces and dimensions on supported devices | Native implementation, device support, complete scan and independent tape evaluation | Future branch, outside current browser-only scope |

A homography maps coordinates on a plane. A four-corner metric reference can rectify that plane; it does not recover an arbitrary object's unseen depth. Camera pose from planar points additionally requires camera calibration. **Inference:** one marker on the front of a shelf cannot establish room length, wall perimeter, ceiling height, floor area or furniture depth. A shelf atlas also needs to preserve per-plane calibration; appearance overlap alone cannot transfer metric scale to a different plane. [OpenCV homography tutorial](https://docs.opencv.org/4.13.0/d9/dab/tutorial_homography.html)

OpenCV provides marker detection and pose estimation using marker size, camera matrix and distortion coefficients. Detection does not itself prove metric accuracy or target coplanarity. A printed ArUco's outer marker dimension is distinct from the surrounding A4 page; measure and record the actual reference used. [OpenCV ArUco detection](https://docs.opencv.org/4.13.0/d5/dae/tutorial_aruco_detection.html)

ChArUco combines marker identification with chessboard corner refinement; OpenCV describes it as useful for precision calibration and partial views. Its board configuration includes square/marker dimensions, and pose estimation requires camera calibration. It still measures a reference plane, not a complete room. [OpenCV ChArUco detection](https://docs.opencv.org/4.13.0/df/d4a/tutorial_charuco_detection.html)

**Proposed measurement seam:** persist marker type/id, verified physical dimensions, source frame and pixel corners, plane id, spine corner evidence, method/version, calibration evidence when available, and rejection reason. Return `null` for unknown plane agreement, ambiguous orientation, clipping, poor corner support or unsupported depth. Compare independent frames for stability. Determine quality thresholds from labelled held-out samples; do not invent a confidence percentage from corner visibility. Sum shelf thickness only for established distinct physical instances and known covered segments; keep the coverage denominator visible.

## iPhone browser versus native spatial capture

WebKit's documented WebXR support is specifically for **visionOS**; the source checked does not establish an iPhone Safari camera/pose/depth path. A LiDAR-capable iPhone does not imply that the existing `getUserMedia` app can read LiDAR. Do not advertise automatic room measurement based on that hardware alone. [WebKit Safari 26.2 features](https://webkit.org/blog/17640/webkit-features-for-safari-26-2/)

WebXR defines capability queries and permission/session requirements; support is device/browser dependent. If investigated later, record `navigator.xr` presence, `isSessionSupported('immersive-ar')`, actual session creation and granted features on the exact device. A positive capability query still does not prove access to camera images, usable depth or metric accuracy. This capability probe is **NOT MEASURED** here. [W3C WebXR Device API](https://www.w3.org/TR/webxr/)

RoomPlan is Apple's Swift framework using camera and LiDAR for parametric room capture; it supplies guidance and recognizes room surfaces and some furnishings. This creates a plausible future room-measurement route, but does not establish individual book identity, spine thickness accuracy, local prices or an insurance-ready inventory. [Apple RoomPlan overview](https://developer.apple.com/augmented-reality/roomplan/), [RoomPlan documentation](https://developer.apple.com/documentation/roomplan)

ARKit exposes scene depth on supported LiDAR devices and requires a support check through `supportsFrameSemantics`. Depth is tied to the camera frame and includes confidence information. A future native capture adapter should preserve frame, pose, calibration, depth confidence and coordinate-system provenance for the same evidence pipeline; independently benchmark narrow book spines rather than assuming room-scale depth resolves them. [Apple ARKit sceneDepth](https://developer.apple.com/documentation/arkit/arconfiguration/framesemantics-swift.struct/scenedepth)

## Evidence gates for the technical showcase

1. **Device capture:** repeat at least one 120-second concurrent preview/voice/upload run per candidate mode. Use the existing preflight ≥95% upload target and record skips separately. Report every preview freeze/dropout, actual resolution and median/p95 capture/upload latency. Higher-resolution and revised queue behavior are **NOT MEASURED**.
2. **Same-plane scale:** start with the existing manual-corner probe on ≥5 independently tape-measured books, then the assignment sample of 20. Include narrow spines, edge-of-image books, perspective, glare and intentional off-plane negatives. Declare sample selection before tuning. Report height and thickness errors separately, mean/median/max, compared/requested counts and every null reason. Final target remains ≤15% error under the declared evaluator; manual-corner success does not establish automatic runtime measurement.
3. **Automatic corners and plane handling:** evaluate marker/spine corner errors and accepted/rejected coverage independently from arithmetic. Compare plain A4 against printed-reference alternatives only if the first gate supplies a reason. Off-plane negatives should abstain; a low error on selected supported cases cannot hide low coverage.
4. **Room feasibility:** remains an independent experiment with tape length/width/height and shape truth. Require a defensible reconstruction method and same-sweep evidence before calculating area. Targets remain ≤10% floor and ≤15% wall-area error. Until then preserve nulls and explicitly mark assignment room requirements unmet. Do not infer geometry from image-model guesses.

Existing probe interface (help verified above): `python -m preflight.probe_measure --input <local-annotations.json> --output <new-local-results.json>`, using the project `.venv/bin/python`. Input records contain `id`, `image_path`, `marker_quad`, `spine_quad`, `same_plane`, `truth_height_cm`, `truth_thickness_cm`; corners run top-left, top-right, bottom-right, bottom-left for portrait A4. The output file must be new because the probe uses exclusive creation. No real input run was performed during this research.

For a later consumer product, offer dimensions as automatic sensor measurements, verified reference-plane measurements, user-supplied records, or unknown—with provenance retained in export. A user-supplied room size is useful information but must never be counted as an independent prediction in the assignment evaluation. Native capture and assisted dimensions need explicit scope decisions after the browser technical showcase succeeds.
